1.0 本讲主线

本讲问题
在一百万个有序数字里找一个数，为什么最多只要比较 20 次？
关键证据
逐步追踪一次查找；对比不同规模下线性查找与二分查找的最坏比较次数。
要解释的机制
有序性让一次比较就能排除一半候选；循环不变式保证目标若存在就一定还在区间内。
迁移目标
判断一个新问题能否「每次排除一半」：猜数字、定位引入 bug 的提交。

Binary search (二分查找)在Sorted array (有序数组)里查找目标：每次看中间元素，根据大小关系丢掉一半，直到找到或区间为空。

1.1 每次比较排除一半

可以复述的判断：因为数组有序，中间元素比目标小，就说明左半边全都比目标小，可以整体丢掉。这一步是二分查找的全部力量来源。

def binary_search(items, target):
    lo, hi = 0, len(items) - 1
    while lo <= hi:                 # 区间 [lo, hi] 非空
        mid = (lo + hi) // 2
        if items[mid] == target:
            return mid
        elif items[mid] < target:
            lo = mid + 1             # 左半边连同 mid 都排除
        else:
            hi = mid - 1             # 右半边连同 mid 都排除
    return -1                        # 区间空了：目标不存在

在 [3, 8, 15, 23, 42, 57, 91] 中找 42：

第几次比较lohimid（值）结论
1063（23）23 < 42，丢掉左半，lo = 4
2465（57）57 > 42，丢掉右半，hi = 4
3444（42）找到，返回 4

代码正确的依据是一条Invariant (循环不变式)：如果目标在数组里，它一定在 [lo, hi] 之内。每次更新 lo 或 hi 只丢掉「已证明不可能」的部分，所以不变式一直成立；区间变空时就能断定目标不存在。

理解检查

如果把 lo = mid + 1 写成 lo = mid，在什么输入下循环会停不下来？

当 lo 与 hi 相邻、且 items[lo] 小于目标时：mid 算出来等于 lo，执行 lo = mid 后区间没有缩小，下一轮完全重复。例如在 [1, 3] 里找 5：lo=0、hi=1、mid=0，1 < 5 → lo 仍是 0。区间必须每轮严格变小，循环才会结束。

1.2 步数为什么是 log₂ n

可以复述的判断：每次比较把候选数量减半，所以 n 个元素最坏只要 ⌊log₂ n⌋ + 1 次比较。

2²⁰ = 1,048,576 ≥ 1,000,000，所以一百万个元素减半 20 次后必然只剩不超过一个候选。n 翻倍，二分查找只多 1 次比较；线性查找的次数也跟着翻倍。这就是Logarithmic time (对数时间)与Linear search (线性查找)的差别。

限制

这张表不能说明什么？

表里只算「比较次数」，没有算排序成本。数组本来无序时，先排序要 O(n log n)；如果只查一次，直接线性扫描 O(n) 反而更省。二分查找的优势来自排好一次、查很多次。

1.3 前提与边界

可以复述的判断：二分查找依赖两个前提：数据按比较的顺序排好，并且能直接跳到中间位置。缺任何一个，算法要么给出错误答案，要么失去速度优势。

易混淆

四个常见错误

  • 对无序数据二分：不会报错，但可能把存在的元素报告为「找不到」，因为被丢掉的那一半里其实可能有目标。
  • 用在链表上：链表没有Random access (随机访问)，走到中间本身就要 O(n) 步，二分的优势消失。
  • 边界差一：<= 写成 <、或 mid ± 1 漏掉，是典型的Off-by-one error (差一错误)：漏查最后一个元素，或陷入死循环。
  • 有重复值时以为返回第一个：上面的写法返回「某一个」匹配位置。要第一个出现的位置，需要找到后继续向左收缩（Python 标准库的 bisect_left 就是这样做的）。

另外，在 Java、C 这类定长整数的语言里，(lo + hi) / 2 在数组极大时可能溢出，惯用写法是 lo + (hi - lo) / 2。Python 的整数不会溢出，所以示例代码里没有这个问题。

1.4 迁移：同一个机制换场景

可以复述的判断：只要一次「检查」能把候选分成「一定不在这边」和「可能在那边」，就能二分。不一定需要数组。

迁移

两个新情境

  • 猜 1–100 的数字，对方只回答「大了 / 小了 / 对了」：每次猜中间值，最多 7 次（2⁷ = 128 ≥ 100）。
  • 定位引入 bug 的提交：已知旧版本正常、新版本有 bug，且中间每个版本只会是「好」或「坏」、一旦变坏就一直坏。测中间那个版本就能丢掉一半历史。git bisect 自动化的就是这个过程。

后一个例子的前提是「好→坏」只变化一次。如果 bug 时有时无，一次测试就不能可靠地排除一半，二分的结论也就不可信。

迁移检查

你在调一个机器学习模型的学习率：太大时训练发散，太小时收敛太慢。能不能二分查找「刚好不发散」的最大学习率？需要什么前提？

可以，前提是单调性：某个阈值以下都不发散，以上都发散。这样每试一个中间值，就能确定阈值在左边还是右边。如果训练结果受随机种子影响很大，同一个学习率时而发散时而不发散，单次试验就不能可靠地排除一半，需要重复试验或换方法。
